隔离技术的边界与选型

——从独立内核、共享内核到 AI Agent 的代码执行环境

虚拟机为应用提供独立的内核，Linux 容器让进程共享宿主机内核，MicroVM 则把虚拟机做得更轻。理解这些区别，也就能看清沙盒如何限制代码的活动范围，以及不同任务需要怎样的执行环境。

01 / VM、容器与沙盒是什么关系？

虚拟机、容器、微虚拟机和沙盒经常出现在同一场讨论里。理解它们，可以先分清两个问题：执行环境怎样实现隔离，以及我们希望用这个环境做什么。

  • 虚拟机（VM）提供一台虚拟计算机，运行独立的客户机操作系统。微虚拟机（MicroVM）是其中更轻量的一类实现，重点在于精简设备模型和启动链路。
  • 容器（Container）把应用及其依赖打包，在共享宿主机内核的基础上隔离进程、文件系统视图和网络。
  • 沙盒（Sandbox）是一种受控的执行环境，用来限制代码能访问的文件、网络和系统能力。它可以由虚拟机、容器或专门的运行时实现。

下面围绕三个问题展开：各自隔离了什么，隔离依靠什么机制，又需要付出哪些运行开销？

02 / 通用虚拟机（VM）：独立操作系统与内核

虚拟机可以理解为在一台物理服务器上创建多台虚拟计算机。每台虚拟机都有自己的虚拟 CPU、内存、磁盘和网卡，并运行一套客户机操作系统（Guest OS）。

2.1 隔离了什么？

  • 独立的操作系统与内核：宿主机运行 Linux，客户机可以运行 Windows，也可以运行另一个版本的 Linux。客户机的内核、系统服务和应用可以单独更新、重启或恢复。
  • 独立的资源视图：客户机使用分配给它的虚拟内存和设备，通过虚拟磁盘、虚拟网卡等接口完成存储和网络操作。
  • 客户机与宿主机之间的边界：在客户机中获得 root 权限，控制的是这台客户机。要进一步控制宿主机，攻击者还需要突破虚拟化边界。

2.2 实现原理与开销

管理虚拟机的这一层软件称为 Hypervisor，也常称为 VMM（虚拟机监视器）。在 Linux 上，常见组合是 KVM + QEMU：KVM 位于宿主机内核中，提供硬件虚拟化能力；QEMU 运行在用户态，负责设备模型和虚拟机管理。

以 x86 平台为例，Intel VT-x / AMD-V 让客户机代码在硬件控制的环境中执行；EPT / NPT 这类二级页表，把客户机使用的物理地址映射到分配给它的宿主机内存。KVM 利用这些机制运行虚拟 CPU、管理客户机内存，QEMU 则为客户机提供磁盘、网卡等设备。

通用虚拟机追求广泛的系统和设备兼容性。设备可以按需配置，引导时可以使用 BIOS/UEFI，也可以直接加载客户机内核。它的资源开销主要来自 VMM、客户机内核和客户机系统服务；启动时还需要完成客户机系统及应用的初始化。

03 / Linux 容器（Container）：共享内核的进程隔离

Linux 容器中的应用依然是宿主机上的一组受限进程。容器运行时为这些进程设置独立的资源视图、资源配额和系统权限，让应用在自己的文件系统和网络环境中运行。

3.1 隔离了什么？

启用相应的命名空间后，容器内的 ps 展示自己的进程视图，ls / 展示自己的根文件系统，网络接口、端口和主机名也可以独立设置。这些视图背后，仍然是同一个宿主机 Linux 内核。

  • 共享内核：容器进程通过系统调用使用宿主机内核。内核漏洞可能成为逃逸入口；宿主机内核崩溃也会中断其上运行的容器。
  • 用户身份映射：User Namespace 可以把容器内的 root 映射为宿主机上的普通用户 ID，分开容器内外的身份。
  • 限制实际权限：Capabilities、Seccomp 和 AppArmor / SELinux 进一步控制进程可以执行的操作。权限由这些机制共同决定，容器内显示的用户名只是其中一部分。

3.2 实现原理与优势

容器隔离由几组 Linux 内核机制组合而成：

  • Namespace（视图隔离）：PID 隔离进程编号与可见范围，Mount 隔离挂载视图，Network 隔离网络设备与协议栈，UTS 隔离主机名，IPC 隔离进程间通信资源，User 管理用户身份映射。
  • Cgroups（资源控制）：为进程组设置 CPU 时间配额、内存上限和 I/O 限额。例如，可以把一组进程的 CPU 使用量限制为两个核心的时间份额，并设置 512 MB 的内存上限。
  • 权限控制：Capabilities 把 root 权限拆成更细的能力；Seccomp 限制允许使用的系统调用；AppArmor / SELinux 根据策略控制进程对文件等资源的访问。

容器的轻量来自共享内核：创建容器时，无需再启动一套客户机内核。容器镜像把应用、依赖和用户态文件系统组织起来，也让开发、测试和部署使用相同的交付单元。这种启动方式和交付效率，使容器适合微服务、CI/CD 和批处理任务。

04 / 微虚拟机（MicroVM）：精简设备与启动链路

Serverless 函数和代码执行平台经常需要创建、运行、回收大量执行环境。AI Agent 执行代码、安装依赖和修改文件时，也需要一个与宿主环境隔离的工作空间。MicroVM 保留独立客户机内核，再通过精简设备模型降低虚拟机的开销。

Firecracker 和 Cloud Hypervisor 都是这一方向的 VMM。Kata Containers 则是一种容器运行时：它启动轻量虚拟机，由客户机中的 kata-agent 管理容器，把虚拟机的隔离能力接入容器工作流程。

4.1 MicroVM 是怎么做“减法”的？

以 Firecracker 为例，它通过 KVM 运行客户机，客户机拥有自己的 Linux 内核。轻量化主要来自对设备模型、启动流程和客户机环境的精简：

  • 精简设备模型：围绕工作负载保留必要设备，减少设备模拟代码、运行开销和客户机能够接触的接口。
  • 缩短启动链路：直接加载客户机内核，省去固件和引导程序的启动步骤；同时精简客户机内核配置与系统服务。
  • 使用 virtio 设备：通过 virtio-net、virtio-blk 等接口提供网络和块存储，通过 vsock 建立宿主机与客户机之间的通信。Cloud Hypervisor 还支持用 virtio-fs 共享宿主机目录。

这些做法减少了虚拟机需要初始化和维护的组件，让它更适合频繁创建与回收。运行一个 MicroVM 时，仍需要为客户机内核、应用和 VMM 分别提供资源。

05 / 沙盒实现与选型

沙盒限制代码可以接触的资源，代码执行平台还要管理任务的生命周期：设置资源与时间上限，隔离不同用户的工作区，并在会话结束后清理临时数据。需要继续使用的项目文件，可以在同一会话中保留，或保存到独立存储。

选择实现方式时，先看要运行什么。Wasm 运行时执行 WebAssembly 模块，并通过宿主提供的接口访问外部资源；Linux 容器依靠共享内核中的隔离机制；gVisor 在用户态实现 Linux 系统调用，减少工作负载直接接触宿主机内核的接口；MicroVM 则提供独立的客户机内核。

如果应用可以编译为 Wasm，可以围绕模块和宿主接口组织沙盒；运行现有 Linux 程序时，可以在容器、gVisor 和 MicroVM 之间选择；需要管理独立操作系统、内核版本或更丰富的虚拟设备时，通用虚拟机更方便。
