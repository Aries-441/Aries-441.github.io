01 / Kubernetes 是什么，解决什么问题

Kubernetes（简称 K8s）是一个开源的容器编排平台，用来部署和管理集群中的容器化应用。我们声明应用要运行哪个版本、保留多少副本，Kubernetes 再把这些要求落实到各台服务器上，并持续维护它们的运行状态。

1.1 从单机容器到集群编排

在只有一两台服务器时，用 docker run 或 Docker Compose 就能把服务跑起来。随着服务器和应用数量增加，需要处理的问题也多了起来：

  • 调度与资源分配：新应用该放在哪台机器上？这台机器能否满足它申请的 CPU 和内存？
  • 故障恢复：容器进程崩溃后，谁来重启？整台服务器宕机后，谁来补建应用副本？
  • 服务发现与负载均衡：应用实例被替换后，IP 可能变化，调用方怎样找到它，又怎样把请求分发给多个副本？
  • 发布与回滚：怎样逐步替换旧版本，减少升级对业务的影响？新版本出问题后，怎样回退？
  • 扩缩容与配置管理：怎样根据流量调整副本数，并把配置、密码等信息与容器镜像分开维护？

Kubernetes 为这些工作提供了统一的管理方式。部署应用时，我们可以面向整个集群描述需求，由系统协调各台机器完成具体操作。

1.2 核心设计思想：声明式 API 与期望状态

理解 Kubernetes，可以先从声明式（Declarative）管理入手。写运维脚本时，我们会安排执行步骤，比如“启动 A，再启动 B，失败后执行 C”。在 K8s 中，还可以直接用 YAML 描述目标：“我希望这个应用运行 3 个副本。”

这份声明描述的是期望状态（Desired State），集群当前的运行情况则是实际状态（Current State）。Kubernetes 中的控制器会不断比较两者，就像空调根据设定温度调节运行一样：声明保留 3 个副本，删掉一个后，系统会补建一个；把期望数量改成 5，系统就继续增加副本。这个持续检查、调整的过程，让实际状态逐步接近期望状态。

02 / 集群双层架构与核心组件

Kubernetes 集群可以按职责分成两部分：控制平面（Control Plane）负责管理集群状态、安排任务；工作节点（Worker Node）负责运行业务容器。在本地学习环境中，这两部分也可以部署在同一台机器上。

2.1 控制平面（Control Plane）

控制平面负责接收配置、保存状态并作出集群层面的决策。下面几个组件各有分工：

  • kube-apiserver（API 服务器）：集群管理的入口。我们提交配置、查询 Pod，控制器读取资源、写入更新，都通过它提供的 API 完成。它负责检查请求者的身份和权限，并在资源写入时按准入规则检查、处理请求。
  • etcd（分布式键值数据库）：保存集群的配置和资源对象，例如应用声明了多少副本、Pod 分配到了哪个节点。API Server 负责读写这些数据，调度器和控制器通过 API Server 获取集群状态。
  • kube-scheduler（调度器）：为尚未分配节点的 Pod 选择一台机器。它会检查节点能否容纳 Pod 申请的 CPU、内存等资源，再结合应用对节点的要求作出选择。选好后，它把绑定结果提交给 API Server，启动工作由目标节点上的 kubelet 接手。
  • kube-controller-manager（控制器管理器）：把多个内置控制器放在同一个进程中运行。每类控制器持续关注自己负责的资源，例如维护应用的副本数量、跟踪节点的工作状态，并在状态发生变化时作出调整。
  • cloud-controller-manager（云控制器管理器，可选）：对接云厂商的 API，处理云节点信息、云路由和云负载均衡器等事务。使用云平台的这些能力时，可以部署相应的云控制器。

2.2 工作节点（Worker Node）与集群插件

工作节点负责运行业务容器。可以先认识与 Pod 的运行和访问有关的三类组件：

  • kubelet（节点代理）：节点上的执行负责人。它从 API Server 获取分配给本机的 Pod，准备所需的存储，调用容器运行时启动容器，并持续检查运行情况、上报状态。
  • Container Runtime（容器运行时）：负责拉取镜像、创建和启停容器，常见实现有 containerd 和 CRI-O。kubelet 通过 CRI（容器运行时接口）与它通信。
  • kube-proxy（网络代理）：维护 Service 的转发规则。它从 API Server 获取 Service 配置，以及记录后端地址和就绪状态的 EndpointSlice。在常见的 Linux 集群中，kube-proxy 根据这些信息配置内核规则，请求随后由内核转发到后端 Pod。一些网络插件也能承担这项工作。

集群还会用到一些基础插件：CoreDNS 提供服务名解析，让应用通过名称找到服务；CNI 网络插件配置 Pod 网络，让不同节点上的 Pod 能够通信；CSI 存储插件对接外部存储，为应用提供持久化卷。

03 / 必须先认识的四类基础资源对象

实际部署应用时，我们会用 YAML 定义资源对象（Resource Objects），再交给 API Server。下面四类对象，经常会出现在一份部署配置中：

资源对象核心定位为什么需要它
PodK8s 中创建和调度的基本单元一个 Pod 可以包含一个或多个紧密协作的容器。它们共享网络，可通过 localhost 通信；需要共享文件时，可以挂载同一个存储卷。
Deployment管理应用的副本与发布更新，常用于无状态应用Deployment 用来声明应用版本和副本数。它通过 ReplicaSet 维护 Pod 副本，例如缺少副本时补建新的 Pod；更新应用时，它负责组织新旧副本的替换，也支持回滚。
Service一组 Pod 的稳定网络访问入口Pod 重建后，IP 地址可能变化。常见的 ClusterIP Service 提供稳定的集群内访问地址，通过标签选择器找到后端 Pod；应用可以使用服务名访问它，后端副本更换时仍使用同一个入口。
ConfigMap & Secret保存应用配置与敏感凭据ConfigMap 保存普通配置，Secret 保存密码、令牌等敏感信息。它们可以作为环境变量传入容器，也可以挂载成文件，让配置独立于镜像维护。

配置更新后，现有进程的环境变量不会自动刷新；通过文件读取配置的应用，需要在文件更新后重新加载。ConfigMap 和 Secret 的文档介绍了具体的使用方式。

相关文档：Pods · Deployment · ReplicaSet · Service

下面用两份配置部署一个 nginx 应用。Deployment 的模板为 Pod 设置 app: web-demo 标签，Service 再通过这个标签找到它们：

yaml
# 1. Deployment：声明“始终运行 2 个 nginx 副本”
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-demo
spec:
  replicas: 2                      # 期望副本数
  selector:
    matchLabels:
      app: web-demo                # 匹配带有该标签的 Pod
  template:                        # Pod 模板，控制器按此模板实例化 Pod
    metadata:
      labels:
        app: web-demo
    spec:
      containers:
        - name: nginx
          image: nginx:1.27
          ports:
            - containerPort: 80
          readinessProbe:       # 就绪检查，影响是否接收普通 Service 流量
            httpGet:
              path: /
              port: 80
            periodSeconds: 5
---
# 2. Service：为上述 2 个 Pod 提供统一的内部访问入口与负载均衡
apiVersion: v1
kind: Service
metadata:
  name: web-demo-svc
spec:
  selector:
    app: web-demo                  # 选择带 app=web-demo 标签的 Pod，后端由 EndpointSlice 维护
  ports:
    - port: 80                     # Service 暴露的端口
      targetPort: 80               # 后端 Pod 容器实际监听的端口

04 / 一个 Pod 是怎样创建并运行起来的

把上面的配置交给 kubectl apply 后，集群会创建两个 Pod，并通过 Service 提供集群内的访问入口。顺着其中一个 Pod 看下去，就能把前面的组件分工串起来：

  1. 提交部署配置：kubectl 将配置发送给 kube-apiserver。API Server 完成身份、权限和配置检查后，把 Deployment 和 Service 保存到 etcd。
  2. 创建 Pod 对象：Deployment 控制器创建 ReplicaSet，ReplicaSet 控制器再根据副本数和 Pod 模板创建 2 个 Pod。这些操作都通过 API Server 完成。此时 Pod 还没有分配到节点，spec.nodeName 为空，处于 Pending 阶段。
  3. 选择运行节点：调度器找到尚未分配节点的 Pod，先过滤掉资源无法满足要求、或不符合调度条件的节点，再对候选节点打分。选好后，它向 API Server 提交绑定结果，Pod 的 spec.nodeName 随之确定。
  4. 在节点上启动容器：目标节点的 kubelet 获取 Pod 配置，准备所需的存储，并通过 CRI 调用容器运行时。运行时创建 Pod 的运行环境，调用 CNI 插件配置网络，再拉取镜像并启动容器。需要挂载 CSI 卷时，由 kubelet 与节点上的 CSI 插件协作完成。
  5. 检查应用是否就绪：kubelet 持续上报 Pod 的运行状态。Running 描述 Pod 的运行阶段，Ready 描述它是否准备好接收流量。上面的 readinessProbe 通过 HTTP 请求检查 nginx：应用还在初始化时，Pod 可能已显示 Running，Ready 仍为 False。
  6. 接入 Service 流量：EndpointSlice 控制器把 Pod 的地址和就绪状态更新到服务后端列表，kube-proxy 随后更新各节点的转发规则。等这些更新传播完成，Service 就能把请求送到新就绪的 Pod。

05 / 把这些组件串起来

回头看这次部署，可以从三个角度记住 Kubernetes 的工作方式：

  • 通过 API Server 协调状态：控制器创建资源，调度器选择节点，kubelet 执行节点上的任务。它们通过 API Server 获取变化、提交结果，再由状态变化推动下一步工作。节点内部则通过 CRI、CSI 等接口完成具体操作。
  • 沿着调度、启动、就绪三个阶段排查：Pod 处于 Pending 时，先看它是否已经分配节点。没有分配，就检查资源请求和调度条件；已经分配，再看镜像、网络和存储的准备情况。spec.nodeName 和事件（Events）能提供线索。Pod 进入 Running 后，再结合 Ready 判断应用是否就绪。
  • 分清容器重启和 Pod 补建：容器进程退出后，kubelet 按 restartPolicy 处理；Pod 被删除或节点失效后，Deployment / ReplicaSet 等控制器负责补建新的 Pod。直接创建的 Pod，其容器也能由 kubelet 重启；用 Deployment 部署应用，还能自动补建副本、管理发布更新。
理解了这条部署链路，再看扩缩容、滚动更新和故障恢复，就能知道该从哪个组件入手。
