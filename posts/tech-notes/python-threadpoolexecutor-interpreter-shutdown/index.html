主线程退出后，为什么
submit() 会报 interpreter shutdown？

——一次跨 threading._shutdown() 与非 daemon 线程生命周期的时序排查

服务进程还在运行，后台消费线程也正常收发消息，但 daemon 线程调用 ThreadPoolExecutor.submit() 却直接抛出 RuntimeError。顺着 CPython 的 threading._shutdown() 往下看，问题出在主线程返回时就已经触发了全局清理。

2026.06.29 CPython 3.9+ 源码追踪 cpython #148280

01 / 现象与触发时序：进程还活着，线程池却已关闭

先看报错现场：进程还活着，后台消费线程也在跑，但轮询线程（poller）调用 ThreadPoolExecutor.submit() 时直接抛出了异常：

text
RuntimeError: cannot schedule new futures after interpreter shutdown

字面上看像是 Python 解释器正在退出，但只要进程里还有别的非 daemon 线程在运行，OS 进程根本不会退出，甚至还能继续存活很久。原因在于 CPython 3.9+ 中，concurrent.futures.thread 的模块级全局变量 _shutdown 绑定的是主线程退出时机，而不是整个进程何时真正结束。一旦主线程返回并进入关闭路径，所有 executor 的 submit() 都会拒绝新任务。

这个问题通常在三个条件同时成立时触发：

  1. main() 不阻塞，启动完后台组件后直接返回；
  2. 进程里还有非 daemon 线程继续运行（例如 gRPC server、Kafka consumer 或第三方 SDK 自己拉起的后台消费线程）；
  3. 某个 daemon 线程在主线程退出之后，才调用 ThreadPoolExecutor.submit()。
python
import threading
from concurrent.futures import ThreadPoolExecutor

# consumer、fetch_task() 和 handle() 由业务代码提供。
pool = ThreadPoolExecutor(max_workers=4)

def poller_loop():
    while True:
        task = fetch_task()  # 等待下一项任务
        # 若第一项任务在全局 _shutdown 置位后才到达，这次提交会抛 RuntimeError。
        pool.submit(handle, task)

def main():
    consumer.start()  # 启动非 daemon 后台线程后立即返回
    threading.Thread(target=poller_loop, daemon=True).start()

if __name__ == "__main__":
    main()  # main() 返回，脚本顶层代码执行完毕，解释器开始收尾。

# 1. threading._shutdown() 调用 _python_exit()，将线程池模块的 _shutdown 设为 True。
# 2. 主线程随后等待剩余的非 daemon 线程退出，包括 consumer 的后台线程。
# 3. 若 poller 在这段等待期间首次提交任务，进程仍存活，submit() 却会报：
#    RuntimeError: cannot schedule new futures after interpreter shutdown

02 / CPython 源码链路追踪（3.11）

2.1 全局 _shutdown 标志是如何被设上的

Lib/concurrent/futures/thread.py 中的关键逻辑如下：

python
# Lib/concurrent/futures/thread.py
_threads_queues = weakref.WeakKeyDictionary()
_shutdown = False
_global_shutdown_lock = threading.Lock()

def _python_exit():
    global _shutdown
    with _global_shutdown_lock:
        _shutdown = True
    items = list(_threads_queues.items())
    for t, q in items:
        q.put(None)          # 给每个 worker 发送退出信号
    for t, q in items:
        t.join()             # 等待已有 worker 退出

# 注册到 threading 内部退出钩子，而非标准库 atexit
import threading
threading._register_atexit(_python_exit)

_shutdown 是模块级全局变量，一旦置位，当前解释器内的所有 ThreadPoolExecutor 实例都会拒绝提交；而 _python_exit() 挂在 threading 的内部退出钩子上，触发时机锚定的是主线程退出，而不是等所有线程结束。

2.2 threading._shutdown() 的两阶段执行顺序

为什么进程没有立刻退出，_threading_atexits 却已经执行完了？下面用伪代码展示 CPython 3.11 的 Lib/threading.py 中 _shutdown() 的执行顺序：

python
# CPython 3.11 · Lib/threading.py 关闭顺序（伪代码）
_threading_atexits = []

def _register_atexit(func):
    _threading_atexits.append(func)

def _shutdown():
    # 1. 主线程结束用户代码后，先执行所有 _threading_atexits
    #    执行到 _python_exit() 时，它会将 concurrent.futures.thread._shutdown 设为 True
    for atexit_call in reversed(_threading_atexits):
        atexit_call()

    # 2. 之后才循环 join 所有存活的【非 daemon 线程】
    #    主线程其实一直卡在这一步等待 SDK 线程结束
    t = _pickSomeNonDaemonThread()
    while t:
        t.join()
        t = _pickSomeNonDaemonThread()

阶段 1 在阶段 2 之前执行。主线程在等待其他非 daemon 线程结束之前，就已经把 concurrent.futures 的全局开关拉死了。

2.3 submit() 的三层检查与延迟创建假象

ThreadPoolExecutor.submit() 在提交任务时会依次检查三道条件：

python
# Lib/concurrent/futures/thread.py
class ThreadPoolExecutor:
    def submit(self, fn, /, *args, **kwargs):
        with self._shutdown_lock, _global_shutdown_lock:
            if self._broken:
                raise BrokenThreadPool(self._broken)
            if self._shutdown:
                raise RuntimeError('cannot schedule new futures after shutdown')
            if _shutdown:
                raise RuntimeError(
                    'cannot schedule new futures after interpreter shutdown')
层级变量含义
第 1 层self._brokenexecutor 实例自身损坏
第 2 层self._shutdown该线程池实例已进入关闭状态。调用 executor.shutdown() 或 worker 响应解释器关闭时，都可能设置这个标志。
第 3 层_shutdown模块级全局标志，主线程退出时被设为 True

本文里的报错命中的是第 3 层，和有没有手动调用过 executor.shutdown() 无关。还有一个更隐蔽的变种：

python
def poller_loop():
    time.sleep(10)
    pool = ThreadPoolExecutor(4)  # __init__ 只初始化队列与锁，不检查 _shutdown
    pool.submit(work)             # 全局关闭检查在此抛错，尚未调用 _adjust_thread_count()

ThreadPoolExecutor 在构造时不检查全局关闭标志，也不创建 worker。因此示例中的线程池可以在主线程返回之后创建成功。第一次 submit() 会先检查该标志并抛错，任务尚未入队，也没有启动 worker。

03 / 版本演变与官方修复进展

这个问题在不同 Python 版本里的表现并不一致：

3.1 历史根源与官方 Bug 确认

2020 年，Antoine Pitrou 提出 bpo-39812（通过 PR #19149 合入 3.9）：为使线程池能在禁止 daemon 线程的子解释器中工作，这次改动移除了线程池对 daemon worker 的依赖，并把 _python_exit() 从普通 atexit.register() 改到了 threading._register_atexit()。CPython 3.8 的线程池已有模块级 _shutdown 标志。3.9 的改动把它的置位时机提前到了等待其他非 daemon 线程之前。

官方 Issue cpython #148280 已将其标记为 type-bug 并打上 3.15 标签。维护者 ZeroIntensity 已接手排查。该 issue 讨论的是：只要仍有非 daemon 线程在运行，线程池就应能继续接受任务。

3.2 为什么多个版本未改：防崩溃与防误杀的取舍

如果不设 _shutdown = True，daemon worker 可能在解释器终结阶段访问已释放状态，引发更严重的崩溃（Victor Stinner 在 Threading shutdown race condition 中详细讨论过这类竞态）；如果提前设 _shutdown = True，则会误杀仍在合法运行的线程。CPython 3.9–3.14 的实现明显更偏保守——宁可提前拒绝 submit()，也不愿在关闭阶段冒崩溃风险。

04 / 修复方案与最小复现脚本

4.1 两种可行改法

方案 A：保持主线程驻留（推荐）——让主线程作为进程生命周期的协调者，通过 threading.Event().wait() 阻塞驻留，并在收到退出信号后按序关闭组件：

python
import signal
import threading
from concurrent.futures import ThreadPoolExecutor

stop_event = threading.Event()

def handle_signal(signum, frame):
    stop_event.set()

def main():
    signal.signal(signal.SIGINT, handle_signal)
    signal.signal(signal.SIGTERM, handle_signal)

    pool = ThreadPoolExecutor(max_workers=4)
    poller = threading.Thread(target=poller_loop, args=(pool, stop_event), daemon=True)
    poller.start()
    consumer.start()

    # 主线程显式阻塞，不触发 _python_exit()
    stop_event.wait()

    # 按依赖反序优雅停机
    poller.join(timeout=5)
    pool.shutdown(wait=True)
    consumer.stop()

方案 B：任务量小时去掉线程池，改为顺序执行——如果轮询批次小、并发并非刚需，直接循环处理反而省去线程池生命周期管理：

python
def tick(self) -> int:
    snapshots = self._get_pending_tasks()
    if not snapshots:
        return 0
    for snap in snapshots:
        self._process_one_safe(snap)
    return len(snapshots)

单独把 poller 改成 daemon=False 可以让进程继续存活。主线程返回后，解释器仍会先执行 _python_exit()，再等待 poller 退出。这段等待期间，poller 提交任务仍会报错。

4.2 最小复现脚本

python
import concurrent.futures.thread as cf_thread
import threading
import time
from concurrent.futures import ThreadPoolExecutor

def mock_poller():
    """模拟 daemon 线程在主线程退出后使用 executor"""
    time.sleep(0.3)
    print(f"_shutdown = {cf_thread._shutdown}")
    pool = ThreadPoolExecutor(max_workers=2)
    try:
        f = pool.submit(lambda: "ok")
        print(f"submit 成功: {f.result()}")
    except RuntimeError as e:
        print(f"submit 失败: {e}")

def sdk_background_thread():
    """模拟非 daemon 线程保持进程存活"""
    time.sleep(5)

if __name__ == "__main__":
    threading.Thread(target=mock_poller, daemon=True).start()
    threading.Thread(target=sdk_background_thread, daemon=False).start()
    # main 返回 -> 主线程退出 -> cf_thread._shutdown = True

排查打印状态时注意区分：threading._shutdown 是 threading 模块里的关闭函数，本文这条 after interpreter shutdown 报错检查的是 concurrent.futures.thread._shutdown 这个布尔变量。
