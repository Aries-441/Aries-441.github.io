01 / 写在前面：这到底是个什么 bug

先说现象：一个原本 11 字节的文件，用 O_TRUNC 覆盖写入 2 字节的 hi，正常来说文件大小就该变成 2。但在 virtiofsd 后端挂 s3fs 的环境里，写完 stat 一看，长度居然还是 11——前两个字节是 hi，后面跟着 9 个 NUL（\x00）。

既不是应用写错了，也不是 close() 闹鬼，问题出在一次看似只读的 xattr 查询上。Guest 执行 open(O_TRUNC) 时紧跟着发了一次 GETXATTR，virtiofsd 为了读这个属性，在宿主机上额外 open 了一次目标文件。偏偏 s3fs 的 open 是带状态的：它看到同一个文件已经打开且没有未刷盘的脏数据，就顺手从 StatCache 里摸出截断前的旧长度 11，直接把本地缓存文件 ftruncate 回了 11 字节。等后面 flush 时，s3fs 就老老实实地把这 11 字节传上了 S3。

目前 PR #2002 已经合入了 getxattr 路径的修复，其余几个 xattr 操作还在 PR #2036 里走评审。下面把整个排查过程、源码链路和内核接口的坑摊开讲清楚；哪些是源码推断、哪些是本地实测，我都会在对应地方标出来。

02 / 正常情况下，覆盖写本该发生什么

复现这个现象只需要三行 shell：

bash
printf 'hello world' > f
printf 'hi'          > f
stat -c '%s' f

第一行先写个 11 字节的文件。第二行的 > 重定向会带着 O_WRONLY | O_CREAT | O_TRUNC 去 open() 文件。按照 POSIX 语义，只要 open() 返回，文件长度就已经清零了；接着 write() 写进去 2 字节，最后 close() 释放文件描述符（fd），不会再去动文件内容。本地文件系统上跑完，stat 吐出来的一定是 2。

顺带提一句：如果文件截断归零之后，又有谁强行把长度撑大到 11，那中间多出来的 9 个字节按规矩必须填零，不会把原来的 llo world 吐回来。记住这一点，后面看到 9 个 NUL 就不会奇怪了。

03 / 诡异的 11 字节和 9 个 NUL

把上面那三行放到 s3fs 作后端的 virtiofs 环境里跑，结果就变成了：

text
11

用 xxd 看内容是 6869 0000 0000 0000 0000 00——hi 后面拖着 9 个 0x00。这说明 O_TRUNC 当时确实把文件截成 0 了（旧数据已经没了），但在 write("hi") 之前或之间，有某个环节又把文件长度拉回了 11，导致新写的 2 字节落在了开头，尾巴上全是撑出来的零。

整张图里最反直觉的就是 GETXATTR 后面跟着的那次 open(O_RDONLY)。应用没调它，Guest 内核也没直接发起 FUSE_OPEN。它是宿主机上的 virtiofsd 在处理 xattr 请求时，为了凑一个能传给 fgetxattr() 的普通 fd，自己顺手在宿主机上调了一次 open()；Host VFS 转手就把这次调用变成了发给 s3fs 的 FUSE_OPEN。灾难就是从这里开始的。

04 / 一次 Guest 操作跨过了哪几层

如果只是一层普通的本地文件系统，virtiofsd 顺手 open(O_RDONLY) 再 close() 一下，大家确实相安无事。但在这个环境里，一次文件操作其实是跨了两道 FUSE 边界：

Guest 里的应用以为自己在读写一块本地盘：请求先过 Guest VFS，由 virtiofs 驱动打包成 FUSE 请求通过 virtio 队列丢给宿主机上的 virtiofsd；virtiofsd 干的是“透传”的活，直接拿宿主机目录当后端调系统调用；可偏偏宿主机上的这个目录本身又是一个 FUSE 挂载点（s3fs），于是 Host VFS 又把请求通过 /dev/fuse 转发给了用户态的 s3fs 进程。

s3fs 为了在对象存储上模拟 POSIX 语义，自己维护了一堆内存和磁盘状态：记元数据与文件大小的 StatCache、管理已打开文件和本地缓存文件的 FdEntity，以及跟踪脏页区间的 PageList。这就埋下了隐患——Guest 和 virtiofsd 都默认 open(O_RDONLY) 是个无害的只读操作，但到了 s3fs 这层，open() 是会直接修改缓存状态的。

3.1 Guest 侧为什么会突然去读 xattr？

在 Linux 内核里，截断文件并不是把 size 改成 0 就完事了，还得顺手检查一下文件上有没有 setuid/setgid 位或者 file capability，免得旧权限留到新写入的内容上。这个检查就要去读 security.capability 这个扩展属性（xattr）。

具体到 Linux v6.13 的代码：open(O_TRUNC) 会一路走到 do_open() → handle_truncate()（fs/namei.c:3439-3455）→ do_truncate()，然后调用 dentry_needs_remove_privs()（fs/open.c:57）。它先看一眼 IS_NOSEC(inode)（fs/inode.c:2216）能不能快速放行；如果没命中，就会调 security_inode_need_killpriv() 去读 security.capability。哪怕文件压根没有 capability，这次查询也会真刀真枪地发一次 GETXATTR 出来（通常返回 ENODATA）。

为什么 IS_NOSEC 没拦住？因为 FUSE 在刷新 inode 属性时会主动清掉 S_NOSEC 标记（v6.13 fs/fuse/inode.c:299-308），逼着后面重新确认一次；而 superblock 级的 SB_NOSEC 只有在 FUSE init 阶段协商了 FUSE_HANDLE_KILLPRIV_V2 才会挂上（fs/fuse/inode.c:1347-1349）。

证据边界说明一下： Issue #1991 里已经明确观察到 GETXATTR 紧跟在 open(O_TRUNC) 后面；把它对应到 do_truncate() 的权限检查，是我结合内核源码做出的推断（写路径上也有同类检查）。由于当时没抓 Guest 侧的完整调用栈，原现场的 GETXATTR 是否百分百来自这一行还不能下死结论。下文为了区分，用大写 GETXATTR 指 FUSE 协议请求，小写 getxattr 指系统调用。

3.2 当无害的 open 撞上有状态的 s3fs

总之，virtiofsd 眼里的请求序列就是这样：

text
OPEN(O_TRUNC)  →  GETXATTR(security.capability)  →  WRITE("hi")

如果后端是 ext4，中间插个 open(O_RDONLY) 根本不会留下痕迹；但后端是 s3fs，同一个路径只要还存在打开的 FdEntity，第二次 open() 就会直接复用它，并按某种规则重新校准本地缓存文件的大小。接下来就看这个“校准”是怎么把 11 字节救回来的。

05 / 罪魁祸首：s3fs 的 StatCache 与额外 open

先说核心发现：那个阴魂不散的 11，既不在本地缓存里，也不在远端 S3 对象里，而是躲在 s3fs 的 StatCache 里。 O_TRUNC 已经老老实实把缓存和 S3 对象都清成 0 了，但 StatCache 没更新，第二次 open 拿它当圣旨，把本地缓存又撑回了 11。

4.1 三套长度状态，各管各的账

理解 s3fs 这里的问题，得先分清它内部的三套长度状态和几个关键组件：

  • StatCache：s3fs 的元数据账本，记着文件大小、mtime 这些信息。
  • FdEntity：管理某个已打开文件的实体。一个路径对应一个实体，里面攥着一个物理缓存文件 fd；每次有进程来 open，s3fs 就发一个逻辑上的 pseudo fd 出去，大家共享同一个物理缓存，直到最后一个 pseudo fd 关闭。
  • PageList 与 IsModified()：FdEntity 内部用来记缓存区间和脏页状态的结构，flush 时上传多少字节全听它的；IsModified() 用来判断当前有没有还没刷盘的修改。

把整个覆盖写过程里这三处长度的变化列成表，分叉一眼就能看出来：

时刻StatCache本地缓存文件S3 对象
覆盖写之前111111
O_TRUNC 之后1100
额外 open 之后11110
写入 hi 并 flush 之后111111

最微妙的是 StatCache 这一列，从头到尾纹丝不动一直是 11。用 boto3 直接调 head_object 去查 S3 远端对象，也证实了中间窗口里 S3 上确实已经是 0 字节了，是在测试跑完之后才变回 11 的：

text
OBJECT_SIZE key=f_hold2 size=0     # O_TRUNC 之后、额外 open 之前
-- after test --
OBJECT_SIZE key=f_hold2 size=11

4.2 顺着 s3fs 源码走一遍

为什么 StatCache 没清掉，又怎么触发了 ftruncate？翻一下 s3fs（commit 6ac9c17e）的 s3fs_open() 就全明白了（下面做了简化）：

c
/* 简化后的 s3fs_open()，行号对应 s3fs 6ac9c17e */
if (StatCache::getStatCacheData()->HasStat(path)) {
    if (!FdManager::HasOpenEntityFd(path))        // 没有打开的实体才删缓存
        StatCache::getStatCacheData()->DelStat(path);
}
check_object_access(path, mask, &st);             // 从 StatCache / HEAD 取元数据
if (flags & O_TRUNC) {
    st.st_size = 0;                               // 截断：长度置 0
    needs_flush = true;
} else if ((ent = autoent.OpenExistFdEntity(path)) && ent->IsModified()) {
    st.st_size = ent->GetSize();                  // 只有已修改才采用内存长度
}
int result = get_object_attribute(path, nullptr, &meta, true, nullptr, true);
if (0 != result)
    return result;                                // notruncate：不把 StatCache 截成 0
autoent.Open(path, &meta, st.st_size, ...);       // 把长度交给 FdEntity::Open

接着看 FdEntity::Open() 拿到 size 之后干了什么：

cpp
/* 简化后的 FdEntity::Open() */
if (-1 != physical_fd) {                          // 本地缓存文件已经打开
    if (0 <= size && pagelist.Size() != size) {
        ftruncate(physical_fd, size);             // 把缓存文件改成 size
        fsync(physical_fd);
        pagelist.Resize(size, false, true);        // 第三个参数 true：新增区间记为 modified
    }
}

两段拼起来，一环扣一环：

  1. 第一次 O_TRUNC open 时文件还没打开，HasOpenEntityFd(path) 为假，s3fs.cpp:3200-3205 确实调了 DelStat。但紧接着 check_object_access() 在截断生效前就去 HEAD 了一次远端旧对象，转手又把 11 写回了 StatCache（s3fs.cpp:3212、:672、:356）——这相当于白删了。
  2. 随后 s3fs_open() 把局部变量 st.st_size 置 0；调 get_object_attribute(..., true) 时走的是 notruncate 分支，刻意不把 StatCache 里的长度截成 0（s3fs.cpp:3248，s3fs.cpp:604-612 的注释写了原因）。接着同步 RowFlush() 把 0 字节对象传上 S3（s3fs.cpp:3225-3229、:3264-3272），并顺手清掉了 PageList 的 dirty 标记，所以此刻 IsModified() 是假（推断）。
  3. 就在这个节骨眼上，virtiofsd 的额外 open 来了。HasOpenEntityFd(path) 此时为真，跳过 DelStat；GetStat() 直接命中缓存，拿到的还是 11。
  4. 因为这次 open 不带 O_TRUNC，且 IsModified() 为假，else if 没进去，st.st_size 保持 11 并传给了 FdManager::Open()（s3fs.cpp:3238-3245、:3255）。日志里会先看到一条 Open(406) [size=-1]（那是 OpenExistFdEntity() 在 fdcache.cpp:695 的探测），紧接着才是真正的 Open(406) [size=11]。
  5. FdManager::Open() 的长度钳制只对 IsModified() 为真的实体生效（fdcache.cpp:558-563），这里直接放行。FdEntity::Open() 看到 physical_fd 已存在，而 pagelist.Size() == 0 不等于请求的 11，二话不说执行 ftruncate(physical_fd, 11)，并调 pagelist.Resize(11, false, true)，把撑出来的 0..10 区间全标成 modified（fdcache_entity.cpp:421-428）。
  6. 等 Guest 的 write("hi") 过来，只覆盖了前 2 字节；后面 flush（fdcache_entity.cpp:1310 起的 RowFlushHasLock）看到 PageList（fdcache_page.cpp:445-455）里 0..10 全是 modified，就把 2 字节内容加 9 个撑出来的零打包传上了 S3。

顺便解释一个可能的疑问：缓存已经被撑大到 11 了，后面 Guest VFS 发 SETATTR 难道不会把它重新截回 0 吗？不会。CubeSandbox 的 virtiofsd 在 init 时宣告了 ATOMIC_O_TRUNC（server.rs:1276），这意味着 O_TRUNC 已经随 FUSE_OPEN 下发并由 s3fs 处理完了；等到 notify_change() 进入 FUSE setattr 时，fuse_do_setattr() 看到 ATTR_OPEN 且 fc->atomic_o_trunc 为真，会直接 goto out 跳过 SETATTR（v6.13 fs/fuse/dir.c:1947-1960）。

所以这个 bug 必须同时凑齐四个条件：已有打开的 FdEntity、第二次 open 不带 O_TRUNC、实体当时 IsModified() == false、且 StatCache 里还留着旧长度。

4.3 本地实验：用四个模式把因果钉死

为了确认不是我脑补出来的，我在本地用 moto_server 搭了个 s3fs 挂载点，写了个 C 测试程序直接模拟几种 open/write 时序（另外两个早期写歪了的失败对照放在附录 A）：

模式操作序列最终大小内容
baselineO_TRUNC open → write 2B → close2hi
second_openO_TRUNC open → 第二次 open/close → write 2B → close11hi + 9 个 NUL
getxattrO_TRUNC open → 第二次 open + fgetxattr + close → write 2B → close11hi + 9 个 NUL
dirty_openO_TRUNC open → write 2B（不 fsync）→ 第二次 open → fsync → close2hi

结果非常干脆：baseline 和 second_open 只差一次平平无奇的 O_RDONLY | O_NONBLOCK open/close，文件就从 2 字节变成了 11 字节。而 dirty_open 刻意在写完 2 字节、还没来得及 fsync（实体还处于 modified）的时候去做第二次 open，结果保住了 2 字节——日志里先是 Open(523) [size=2]，然后 Open(406) [size=-1]，说明 IsModified() 确实起到了保护作用。

s3fs 的 debug 日志把整个过程拍得清清楚楚：

text
10:18:46.223 Open(406) [physical_fd=-1][size=0][flags=0x8201]   # O_TRUNC open
10:18:46.229 RowFlushHasLock [physical_fd=21]                   # 对象同步刷成 0
10:18:46.233 s3fs_open flags=0x8800                             # 额外一次 open
10:18:46.233 Open(406) [physical_fd=21][size=-1][flags=0x0]     # 探测实体，不改大小
10:18:46.233 Open(406) [physical_fd=21][size=11][flags=0x8800]  # 真正 open：size=11

再用 strace -f -e trace=openat,ftruncate 看一眼宿主机上的系统调用，实锤同一个物理缓存 fd（21）先被 899 号线程截成了 0，4 毫秒后又被 926 号线程拉回了 11：

text
openat(AT_FDCWD, "/tmp/s3fstmp.7GxW5X", O_RDWR|O_CREAT|O_EXCL, 0600) = 21
ftruncate(21, 0)    = 0      # O_TRUNC（线程 899）
ftruncate(21, 11)   = 0      # 第二次 open（线程 926）

跑 getxattr 模式时记得挂载参数要带上 -o use_xattr，不然 s3fs 压根不注册 getxattr 回调，内核直接返回 EOPNOTSUPP。加上之后，fgetxattr(fd, "security.capability", ...) 返回 ENODATA，日志里出现 s3fs_getxattr，最终同样变成 11 字节。

再次划清实验边界：本地实验是直接在 s3fs 挂载点上模拟“截断后、写入前插一次 open”，没有拉起完整的 Guest + virtiofsd 链路重抓 OPEN → GETXATTR → WRITE。它把 s3fs 侧的因果闭环了；virtiofsd 侧的链路靠源码和 Issue #1991 的记录支撑。

06 / 修复之路：O_PATH、procfs 与 CLONE_FS

既然知道祸根是 virtiofsd 读 xattr 时多做了一次普通 open，那修法看起来很简单：别 reopen 不就行了？但真动手改代码时，Linux VFS 和系统调用的限制会一步步把你推成一条连环套：

5.1 改用 O_PATH，绕开目标文件系统的 open

在 Linux 里，带 O_PATH 打开文件只会建立一个路径引用（不能用来读写数据），VFS 里的 do_dentry_open() 遇到 O_PATH 会把 f_op 换成 empty_fops 然后提前返回，压根不会调底层文件系统的 ->open——自然也不会触发 s3fs 的 FUSE_OPEN。

修复前，virtiofsd 读普通文件的 xattr 是这么干的：

rust
let file = self.open_inode(inode, O_RDONLY | O_NONBLOCK)?;  // 额外一次 open
unsafe { libc::fgetxattr(file.as_raw_fd(), ...) }

file 在函数返回时 drop，紧接着触发 close()。修复后改成直接拿 O_PATH fd：

rust
let file = data.get_file()?;       // O_PATH fd：File 模式复用已保存的 fd，Handle 模式按需 open(O_PATH)
// 用 /proc/self/fd 的相对路径做 xattr

默认的 File 模式（InodeFileHandlesMode::Never）在 inode store 里本来就存着 O_PATH fd，直接复用；file-handle 模式则是按需 open(O_PATH) 一下。不管哪种，都不会再产生那次 O_RDONLY | O_NONBLOCK 的 FUSE_OPEN。

5.2 为什么不能直接把 O_PATH fd 喂给 fgetxattr()？

遗憾的是，直接调 fgetxattr(opath_fd, ...) 会吃一个 EBADF。因为在内核里，fgetxattr() 本质上是 path_getxattrat(fd, NULL, AT_EMPTY_PATH, ...) 的一层薄封装；它内部用 CLASS(fd, f) → fdget() 去取 fd，而 fdget() 带着 FMODE_PATH 过滤掩码，看到 O_PATH fd 直接当成 EMPTY_FD 拒掉了。

纯 fd 接口走不通，就只能绕回路径型接口。

5.3 借道 /proc/self/fd/N 与 fchdir

Linux 的 procfs 给每个打开的 fd 都挂了一个 magic link：/proc/self/fd/N。内核解析这种 magic link 时会直接顺藤摸瓜找到 fd 背后的 inode，不会重新调底层文件系统的 open()。而且因为它是跟 fd 绑定的，哪怕文件在外部被 unlink 或 rename 了，只要 O_PATH fd 还在手里，xattr 操作依然能落到正确的 inode 上。

virtiofsd 的做法是启动时先打开 /proc/self/fd 目录并把目录 fd 钉住（这样就算后面 /proc 被卸载或遮盖也不怕，也不用每次从根目录重新走路径）。每次需要读 xattr 时：

  1. fchdir(proc_self_fd) 把当前线程的工作目录（CWD）切到 procfs 目录；
  2. 用相对路径 "N"（N 是 O_PATH fd 号）调用 getxattr()；
  3. 用完立刻 fchdir(root_fd) 切回来。

这时候 GETXATTR 和可能伴随的 GETATTR 还是会发给 s3fs，但那个会改写缓存长度的 FUSE_OPEN 彻底消失了。

这里顺便记一个小细节：CubeSandbox 的 root_fd 指的是宿主机的 /（mod.rs:466-467 注释写着 “pointing to the / directory”），而上游 virtiofsd 用的是 orig_wd_fd 保存并恢复原本的 CWD。对 virtiofsd 这种不靠 CWD 干活的守护进程来说区别不大，算是一处实现差异。

5.4 多线程一跑就竞态：unshare(CLONE_FS)

切 CWD 看着挺美，但在多线程下会出大事。Linux 同一进程里的线程默认共享同一个 fs_struct——也就是说，所有 worker 线程共用一个 CWD：

text
worker A: fchdir(/proc/self/fd) → 准备 getxattr("10")
worker B: fchdir(/proc/self/fd) → 完成自己的 getxattr → fchdir(root_fd)
worker A: 解析 "10" 时，CWD 已经被 B 切回根目录……

A 正准备解析相对路径 "10"，B 刚好干完活把全局 CWD 切回了根目录，A 要么找不到文件，要么直接把请求打歪。我在实验 D 里用两个线程加 pthread barrier 做了确定性交错：共享 fs_struct 时，两个线程的 CWD 确实会互相踩踏；每个线程启动后调一次 unshare(CLONE_FS) 拆出独立的 fs_struct，才各自清净。

上游 virtiofsd 其实早就在 main.rs 的线程池里加了 per-thread unshare(CLONE_FS)。但 CubeSandbox 是把 PassthroughFs 当库嵌进 VMM 里的，队列 worker 由 virtio-devices/src/fs.rs 自己拉起，没走上游的 main.rs，导致漏掉了这一步。PR #2002 把它补到了 VMM 的 worker 入口，并且加了门控：只有开启了 xattr || security_label || xattrmap.is_some() 才做 unshare，免得不需要 xattr 的场景平白被 seccomp 拦住；而一旦开了这些功能却 unshare 失败，worker 会直接报错退出整个 VMM——宁可启动失败，也不能带着 CWD 竞态裸奔。

5.5 这套方案的边界

  • 强依赖 procfs：如果运行在极度收紧、/proc 被屏蔽或受 LSM 限制的容器环境里，/proc/self/fd/N 解析失败，xattr 就会跟着挂。
  • 开销：每个 worker 线程多一份 fs_struct，每次 xattr 多两次 fchdir 系统调用。
  • 符号链接（symlink）语义：对于用 O_PATH | O_NOFOLLOW 打开的符号链接，如果走 magic link 去读 xattr，可能会 follow 到链接指向的目标文件（guest 可控的主机路径）。这是上游 work item #230 里记录的风险模型（并非在 CubeSandbox 里已复现出漏洞），需要显式的 no-follow 处理。这块我本地没做专门实验，点到为止。

5.6 还没完：其余 xattr 操作与测试空白

PR #2002 只修了 getxattr。在合入后的 HEAD 上，setxattr、listxattr、removexattr 依然保留着 is_safe_inode → open_inode(O_RDONLY | O_NONBLOCK) 的老路子。后续的 PR #2036 正在把同一套改造扩过去（同时保留 setxattr() 清除 capability 的行为并补回归测试），截至 2026-11-10 还没合入。

测试方面，PR #2002 描述里写了 virtiofsd 51 项单测全过、S3 集成检查 82/82（41 项 Guest 本地 /tmp + 41 项 s3fs /mnt/data）通过，撤掉修复的对照 shim 挂了 21 项（不过这些集成检查是在 rebase 到最新 master 之前跑的）。但有一块明显空白：PR 新增的 4 个单测全是单线程，根本测不出两个 worker 互相覆盖 CWD 的并发竞态——review 时也有人提过，但没被采纳。这也是为什么我单独补了实验 D 来验证。

07 / 延伸：Linux 的 *xattrat() 靠不靠得住？

写到这里很自然会想到：Linux v6.13 不是刚加了一组新的 *xattrat() 系统调用吗？能不能用它直接干掉上面这套 /proc/self/fd + fchdir + CLONE_FS 的杂技？

先说答案：在只拿着目标文件 O_PATH fd、没有可用路径的场景下，目前的 mainline 内核还不行。

6.1 新接口长什么样

v6.13 引入的四个系统调用（x86_64 编号 463–466）把值和标志位塞进了 struct xattr_args，并支持传 AT_EMPTY_PATH 或 AT_SYMLINK_NOFOLLOW：

c
setxattrat(int dfd, const char *pathname, unsigned int at_flags,
           const char *name, const struct xattr_args *uargs, size_t usize);
getxattrat(int dfd, const char *pathname, unsigned int at_flags,
           const char *name, struct xattr_args *uargs, size_t usize);
listxattrat(int dfd, const char *pathname, unsigned int at_flags,
            char *list, size_t size);
removexattrat(int dfd, const char *pathname, unsigned int at_flags,
              const char *name);

用起来分两种姿势——目录 fd 配相对路径，或者纯 fd 配 AT_EMPTY_PATH——关键在于它们在内核里走的是两条完全不同的路：

c
/* 形态一：dirfd + 相对路径 */
getxattrat(dirfd, "path", 0, "security.capability", &args, sizeof(args));
/* 形态二：纯 fd + AT_EMPTY_PATH */
getxattrat(fd, NULL, AT_EMPTY_PATH, "security.capability", &args, sizeof(args));

6.2 实测 6.13 与 6.19：纯 O_PATH fd 依然吃 EBADF

前面提过，path_getxattrat() 在 AT_EMPTY_PATH 分支用的是 fdget()，会把 O_PATH fd 过滤成 EMPTY_FD 返回 EBADF；只有带路径的形态一会走 path_init() → fdget_raw()（mask=0），从而放行 O_PATH 的目录 fd。

为了确认，我在 QEMU 里分别起了一遍 Ubuntu mainline 6.13 和 6.19 实测，结果几乎完全一样（成功项返回测试 xattr 的长度 2）：

调用6.136.19
fgetxattr(O_PATH fd, ...)EBADFEBADF
getxattrat(O_PATH fd, NULL/"", AT_EMPTY_PATH, ...)EBADFEBADF
setxattrat / listxattrat / removexattrat 同上EBADFEBADF
getxattrat(O_RDONLY fd, "", AT_EMPTY_PATH, ...)成功（ret=2）成功（ret=2）
getxattrat(O_PATH 目录 fd, "相对路径", 0, ...)成功（ret=2）成功（ret=2）
getxattrat(AT_FDCWD, "/proc/self/fd/N", 0, ...)成功（ret=2）成功（ret=2）
getxattrat(AT_FDCWD, NULL, AT_EMPTY_PATH, ...)EBADFENODATA

最后一行 AT_FDCWD + NULL pathname 在 6.19 变成 ENODATA（当前工作目录没有该属性）是 f520bed25d17（v6.15）顺手修掉的另一个边界，只改了 setxattrat 和 getxattrat，跟 O_PATH 没关系。

维度旧普通 reopenCubeSandbox 修复*xattrat() 路径型
目标定位普通 fdO_PATH fd + procfs magic link目录 fd + 相对路径
是否普通重新打开是否否

结论很直白：如果你手里正好有父目录 fd 和文件名，用路径型 *xattrat() 最干净，既不 reopen 也不折腾 CWD；但如果文件已经被 unlink/rename 了、手里只攥着一个 O_PATH fd，在主线内核合入那组补丁之前，依然得靠 procfs（用 /proc/self/fd/N 绝对路径也行，fchdir 只是 virtiofsd 选的一种写法）。

08 / 写在最后

回过头看，整个 bug 其实就浓缩在最初那几行输出里：

console
$ printf 'hello world' > f
$ printf 'hi' > f
$ stat -c %s f
11
$ xxd f
00000000: 6869 0000 0000 0000 0000 00              hi.........

做跨层系统排查，最容易掉坑里的地方就是下意识觉得“某个接口只是读一下，肯定没副作用”。在 POSIX 和 ext4 上，open(O_RDONLY) 确实人畜无害；可一旦下面接了个靠缓存模拟语义的用户态文件系统（比如 s3fs），它内部的 StatCache、本地缓存文件和远端对象各记各的账，一次额外的 open 就足以把刚刚截断归零的状态又掰回过去。

而工程上的修复也往往不是改一行就能收工。为了干掉这一次 reopen，一路被系统调用的限制推着走：换 O_PATH、绕 /proc/self/fd、切 fchdir，最后还得补上 unshare(CLONE_FS) 防止多线程把彼此的 CWD 玩坏。

最后交代一下背景和归属：这个问题最早是 CubeSandbox Issue #1991 的报告者抓出来的；PR #2002（Aries-441，2026-10-23 合入）修掉了 getxattr，其余 xattr 操作在 PR #2036 跟进中。我也参与了修复和验证，文中的 s3fs 复现实验、日志抓取和内核对比测试都是我自己本地跑完核对的。

09 / 附录 A：排查时踩过的两个对照坑

写实验验证 IsModified() 的时候，我前两版对照设计得有问题，虽然结果数字“看起来对”，但其实走错了分支，记下来免得后来人踩同样的坑：

  • 第一版 after_write：当时想“写完 2 字节、close 之后再做第二次 open，看会不会撑回 11”。结果确实是 2 字节，但我翻日志发现 GetFdEntityHasLock 返回了 pseudo_fd=-1，接着 DelStat、重新 HEAD、再 Open(406) physical_fd=-1 size=2。原来 close() 把最后一个 pseudo fd 关掉后，FdManager::Close 直接把实体从 fent 里删了，根本没走到“复用已打开实体”那条分支。完整序列：O_TRUNC open → write 2B → fsync → close → 第二次 open。
  • 第二版 after_write_open：吸取教训改成写完不 close 就做第二次 open，但我在第二次 open 前多调了一句 fsync。fsync 会触发 RowFlush 并调 ClearAllModified，等第二次 open 进来时 IsModified() 已经是 false 了（此时 HEAD/StatCache 已经是新刷上去的 2 字节），测出来的其实是已 flush 状态。完整序列：O_TRUNC open → write 2B → fsync → 第二次 open → close。
  • 忘了加 -o use_xattr：第一版跑 getxattr 模式时忘了开这个挂载参数，fgetxattr 直接返回 EOPNOTSUPP(95)，日志里一条 s3fs_getxattr 都没有，等于测了个寂寞。加上之后返回 ENODATA(61)，才算真正走进 s3fs 的 xattr 路径。

所以复现这种缓存状态相关的 bug，光看最终字节数很容易被骗过去，一定要对照 debug 日志确认代码到底走了哪条分支。
